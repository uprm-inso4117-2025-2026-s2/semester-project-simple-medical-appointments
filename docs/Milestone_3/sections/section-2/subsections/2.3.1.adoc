===== Supabase Integration

The system integrates with Supabase for authentication and data storage. This integration is centralized in `backend/app/supabase.py`.


[source,python]
----
def init_supabase(app):
    [.added]#"""Initialize the Supabase client from Flask app config and attach it to the app.
    Call this inside create_app() after loading config.
    Routes can access the client via current_app.supabase or by importing supabase from this module.
    """#
    global supabase

    if app.config.get("TESTING"):
        supabase = None
        app.supabase = None
        return None

    url = app.config.get('SUPABASE_URL')
    key = app.config.get('SUPABASE_KEY')

    if not url or not key:
        raise RuntimeError(
            [.changed]#'Supabase environment variables are missing. '
            'Set SUPABASE_URL and SUPABASE_KEY (or VITE_SUPABASE_URL / VITE_SUPABASE_ANON_KEY) in backend/.env'#
        )

    supabase = create_client(url, key)
    app.supabase = supabase
    return supabase
----

By initializing the client once and attaching it to the application, the system avoids duplicating configuration logic across different components.

An important detail is the conditional behavior during testing. When the application runs in testing mode, the Supabase client is disabled. This prevents external dependencies from affecting test execution and ensures that tests remain fast and reliable.

This abstraction centralizes how requests are constructed and executed. Instead of writing HTTP logic in every endpoint, the system delegates this responsibility to a single function.

This design improves maintainability. If the way requests are handled needs to change, it can be updated in one place without affecting the rest of the codebase. It also ensures consistent error handling and response parsing across all interactions with Supabase.

===== [.added]#Domain Typing Strategy for Scheduling#

[.added]#The scheduling implementation benefits from explicit domain types because appointment booking combines several values that are easy to confuse when represented only as strings or dictionaries. The intended typing strategy introduces `PatientID`, `Doctor`, `TimeSlot`, and `Appointment` as named concepts for the booking workflow. `PatientID` and similar identifiers can be represented with `NewType`, while richer concepts such as `Doctor` and `TimeSlot` can be represented with frozen dataclasses. Appointment records can be represented with a `TypedDict` or dataclass that names the patient, doctor, slot, and status fields.#

[.added]#A non-trivial booking function should therefore accept values such as `patient_id: PatientID`, `doctor: Doctor`, `requested_slot: TimeSlot`, and `existing_appointments: Sequence[Appointment]` instead of raw primitive values. This makes the function signature communicate the domain rule being enforced: a patient books a particular doctor's time slot, and the implementation checks that the slot belongs to that doctor and does not overlap an active appointment. The type checker cannot replace all scheduling tests, but it can catch category mistakes earlier and make the code easier to review.#

[.added]#Side-effecting action functions use `None` as Python's equivalent of `Unit` when their purpose is to change state rather than produce a new value. For example, a cancellation action may return `None` after persisting the transition to `cancelled`; failure should be represented through an exception or an explicit result type. This matches the conceptual `Result Unit Error` signatures used in the design model and clarifies why action functions differ from query functions that return domain data.#
