=== *Other Activities than Just Developing Source Code*

==== Domain Engineering

[.changed]#Domain engineering in this project is centered on the analysis of a medical appointment scheduling system implemented in the repository (currently maintained in a non-main development branch).# This includes identifying how entities such as patients, providers, and appointments are represented in the codebase, and how scheduling constraints are enforced through the current implementation logic.

[.changed]#Instead of remaining at a purely theoretical level, domain understanding is derived directly from the existing modules handling scheduling workflows, repository data models, and service-layer logic responsible for appointment creation, updates, and conflict resolution.#

[.added]#Due to the current repository structure, where some features and tests are not located in the main branch, domain analysis also considers branch-specific implementations to ensure completeness of the system understanding.#

[.changed]#For this project, domain engineering is the work of turning the rough sketches into a usable scheduling vocabulary. That includes deciding, for example, how `Appointment`, `TimeSlot`, `Waitlist`, `Referral`, and `InsuranceAuthorization` differ, and how actions and events around them should be described without conflating them.#

This ensures that the system-to-be represents real-world behavior as currently implemented, rather than assumptions detached from the actual codebase structure.

==== Requirements Engineering

[.changed]#Requirements engineering in this project is directly derived from the implemented behavior of the medical appointment scheduling system, rather than abstract domain descriptions.# Functional requirements are extracted by analyzing existing services, controllers, and database models that define appointment creation, modification, and validation rules.

[.changed]#Traceability is maintained by linking requirements to specific modules and (in some cases) branch-based implementations where relevant functionality exists but has not yet been merged into the main branch.#

[.added]#Given that some tests and supporting documentation are distributed across development branches, requirements analysis explicitly accounts for these artifacts to avoid losing traceability coverage.#

[.changed]#Requirements engineering in this project means converting those domain concepts into verifiable statements about booking, cancellation, confirmation, waitlists, reminders, and availability management, together with traceability from needs, domain concepts, and testing artifacts.#

This ensures alignment between observed system behavior and documented requirements.

==== System Design and Architecture

[.changed]#System architecture in this project reflects the current implementation of the medical appointment scheduling system within the repository, including service-layer separation, data models, and scheduling workflow orchestration.#

[.changed]#Architectural decisions are influenced by the existing code organization, which includes multiple development branches containing active features that are not yet consolidated into main.#

[.added]#As a result, the architectural description is based on a merged conceptual view of the system, combining main branch structure with relevant branch-specific implementations to accurately represent system behavior.#

[.changed]#Architecture work is not just a generic layering exercise here. It includes deciding which parts of scheduling belong to explicit domain services, which API surfaces exist on the current branch, and how frontend and backend responsibilities are separated so that scheduling rules are not hidden inside UI code or route wrappers.#

==== Verification and Validation

[.changed]#Verification and validation activities are based on the available testing infrastructure in the repository, including unit and integration tests where present in active development branches.#

[.changed]#Test-Driven Development and Behavior-Driven Development practices are applied where test suites are available, although some tests referenced in documentation are currently located outside the main branch or have been reorganized during development.#

[.added]#To address this, validation also includes manual traceability checks against branch-specific test suites and execution of available tests across development branches when necessary.#

[.changed]#Verification and validation activities in this project are tied to specific artifacts on `main`: backend unit tests for scheduling logic, backend BDD scenarios, a lightweight CI workflow, and formal reasoning over a concrete scheduling function. Where an activity is still partial, the report now states that limitation explicitly instead of describing an implementation that is not present on the branch.#
