=== Performance Testing for High Demand Appointment Booking
:author: Pedro A. Morales

==== Introduction

Performance testing evaluates how a system behaves under expected, unexpected, and peak workloads. 
In healthcare scheduling systems, performance is critical because large numbers of 
patients may attempt to book appointments simultaneously. If the system cannot handle 
high demand, users may experience slow response times, failed booking attempts, or 
duplicate appointments.

The *Simple Medical Appointments* system allows patients to search for doctors, view 
available appointment slots, and confirm bookings. Performance Testing ensures that 
the appointment booking workflow remains reliable when many users interact with the 
system at the same time.

==== Appointment Booking Workflow

The patient scheduling process involves multiple interactions between the ui, backend, and database.

[source,text]
----
Patient
   |
   v
Search Doctors / Clinics
   |
   v
Retrieve Available Appointment Slots
   |
   v
Select Time Slot
   |
   v
Submit Booking Request
   |
   v
Validate Slot Availability
   |
   v
Database Transaction
(Check slot not already reserved)
   |
   v
Create Appointment Record
   |
   v
Send Confirmation
----

Performance issues may occur if many users attempt to reserve the same appointment 
slot or query appointment availability at the same time.

=== Performance Risks

The main performance risks associated with appointment scheduling include:

==== *Concurrent Booking Conflicts:* 
Multiple users attempting to book the same time slot simultaneously may lead to race 
conditions or duplicate appointments.

==== *Database Contention:*

High volumes of booking transactions may slow database operations responsible for 
checking slot availability and writing appointment records.

==== *Slow System Response:*

Heavy server load may increase response times for availability queries or booking 
confirmations, negatively impacting the patient experience.

==== *Server Resource Exhaustion:*

Large spikes in traffic may overload application servers or APIs responsible for 
processing appointment requests.

=== Performance Testing Strategy

The performance testing strategy focuses on simulating real-world usage scenarios to 
measure system behavior under load.

The strategy evaluates:

==== *Concurrency:*

How the system behaves when multiple users attempt to book appointments simultaneously.

==== *Response Time:*

How quickly the system returns results when patients search for available appointment 
slots or confirm bookings.

==== *Throughput:*

The number of booking requests the system can process within a specific time frame.

==== *Database Performance:*

Transaction time required to validate slot availability and create appointment records.

=== Load Testing Scenarios

To simulate realistic usage conditions, several load levels are tested.

==== *Scenario 1 – Moderate Load*

- 50 concurrent users searching and booking appointments
- Expected system response time below acceptable thresholds
- No duplicate bookings occur

==== *Scenario 2 – High Load*

- 100–200 concurrent users interacting with the scheduling system
- Slight increase in response time but system remains stable

==== *Scenario 3 – Peak Demand*

- 500 or more concurrent users attempting to book appointments
- System must maintain booking integrity and avoid data inconsistencies

=== Impact on Patient Experience

Performance testing improves reliability by ensuring that the scheduling system 
continues functioning correctly during high demand periods. By identifying system 
bottlenecks before deployment, developers can prevent slow responses, booking 
conflicts, and service interruptions.

This ensures patients can successfully schedule appointments even during peak usage 
periods, improving both system reliability and overall patient experience.

=== Fuzz Testing for Input Validation in Appointment Booking
:author: Pedro A. Morales

==== Introduction

Fuzz Testing is a software engineering technique or principle used to flag and expose unexpected, malformed, or random inputs. This testing method helps evaluate how a system behaves if exposed to those types of issues. Unlike traditional testing, which relies solely on predefined test cases, fuzz testing automatically generates large volumes of diverse inputs to identify hidden bugs and system failures. 

Inside the system, patients interact with multiple input fields and APIs while filling out appointment forms. It is critical to ensure that these inputs are properly validated in order to maintain system reliability and preven crashes or invalid data states.

This lecture topic focuses on applying fuzz testing to the appointment booking workflow for system robustness and error handling improvement.

==== Goal

Design a fuzz testing strategy for the appointment booking workflow that evaluates the system’s robustness when handling unexpected, malformed, or extreme input values. The goal is to identify failures inside features like input validation, API handling, and scheduling logics that could lead to crashes, incorrect behavior, or invalid appointment creation.

==== Proposed Solution

Develop a structured fuzz testing approach targeting both frontend inputs and backend API validation.

Scope includes:

- Patient input fields (name, contact information, appointment notes)
- Appointment booking API payloads
- Query parameters for retrieving availability
- Scheduling inputs (date, time, doctor selection)

The strategy simulates abnormal and edge-case inputs to observe system behavior under unexpected conditions. The focus is on robustness and validation handling rather than security measurements.

==== Fuzz Testing Model

Fuzz testing will be implemented using input manipulation and random data generation.

==== Input Categories

- Extremely long strings
- Empty or null inputs
- Special characters and Unicode
- Invalid date/time formats
- Malformed structured data (JSON payloads)

==== Objective

Identify system weaknesses such as:

- Application crashes
- Unhandled exceptions
- Incorrect API responses
- Invalid database insertions

The system must handle all inputs gracefully without compromising stability.

=== *Performance Testing — User Management Authentication Flow*
:author: pierreg-vales

This section applies the *performance testing* lecture to the User Management
feature of the Simple Medical Appointments backend. Load tests were designed
and executed against the login-adjacent and token-protected endpoints to
measure *throughput*, *latency*, and *error rate* at three increasing levels
of concurrent users, in order to determine where and how performance degrades.

All test artefacts live under `backend/tests/performance/`. HTML evidence
reports are stored at `backend/tests/performance/reports/`.

==== *Concepts Applied*

*Performance testing* evaluates how a system behaves under a given workload.
It answers questions about speed, stability, and scalability rather than
functional correctness.

*Load testing* is a sub-type of performance testing in which the system is
subjected to an anticipated, realistic number of concurrent users. The goal is
to verify that the system meets its *response time* and error-rate requirements
within the expected operational range.

*Stress testing* is a sub-type of performance testing that pushes the system
beyond its expected load to find the breaking point — the user level at which
latency explodes or errors begin. Unlike load testing, stress testing is
intentionally destructive. The 100-concurrent-user level in this report begins
to approach stress-testing territory, as it is roughly 10× a realistic
day-to-day peak for a small clinic application.

*Throughput* is the number of requests the system successfully completes per
second (req/s). Higher throughput under the same latency budget indicates
better scalability.

*Response time* (also called *latency*) is the elapsed time from the moment a
client sends a request to the moment the last byte of the response is received.
*Average response time* and *p95 latency* are the primary latency metrics
reported at each load level.

*p95* is the response time that 95% of requests fall at or below. It
characterises the tail of the latency distribution. A system with a low mean
but a high p95 has occasional slow outliers that degrade the user experience
even when the typical request is fast.

==== *Architecture and Test Design*

Authentication in this application is client-side: the browser calls Supabase
Auth and receives a signed JWT access token. That token is passed as a
`Bearer` header on every subsequent request to the Flask backend. Flask
verifies the token using the project's JWT secret and, once validated, executes
the route handler.

Locust cannot replay a real Supabase sign-in for every virtual user. Instead,
Locust *pre-crafts* HS256 tokens signed with the real `SUPABASE_JWT_SECRET`
stored in `backend/.env`. The companion `test_server.py` patches
`auth_middleware.verify_jwt` to accept these HS256 tokens, while all Supabase
*database* calls (availability rules, doctors, provider settings) go to the
real hosted Supabase project over the network.

The endpoints under test are:

* `GET /api/health` — no auth, used as a baseline to isolate pure Flask
  routing overhead.
* `GET /api/doctors/:id/available-slots?date=YYYY-MM-DD` — requires a Bearer
  token; exercises JWT verification and three sequential Supabase REST API
  calls (availability_rules, doctors, provider_settings).

Each virtual user runs two weighted tasks with a think time of 1–3 seconds
between them: health check (weight 1) and available-slots lookup (weight 4).
The 4:1 weight reflects realistic traffic where authenticated data access
dominates anonymous requests.

|===
| Level | Concurrent users | Spawn rate (users/s) | Duration

| Low   | 10  | 2  | 60 s
| Mid   | 50  | 5  | 60 s
| High  | 100 | 10 | 60 s
|===

HTML reports with full response-time histograms and RPS charts are included
as evidence at `backend/tests/performance/reports/load_{10,50,100}_users.html`.

==== *Analysis*

*Throughput scales linearly — server is not the bottleneck.*
Aggregate throughput grew from 2.23 → 10.40 → 21.01 req/s across the three
load levels. This near-linear scaling confirms the Flask server was not
saturated at any tested level. The bottleneck at all three levels was the
users' own think time (1–3 s between tasks), not server processing capacity.

*Latency is dominated by Supabase API round-trip time.*
The protected endpoint averaged 2 471–2 551 ms at all load levels. The route
makes three sequential Supabase REST API calls, each adding a full HTTPS
round-trip to the hosted infrastructure. The mean response time held stable
across all load levels, confirming no saturation effect within the tested range.

*Latency did not degrade noticeably with increasing load.*
The p95 for the slots endpoint moved from 3 000 ms at 10 users to 2 500 ms
at 100 users — a slight improvement due to sample-size convergence, not
degradation.

*Zero error rate at all load levels.*
No request failed across all 1 971 total requests in the combined runs. The
authentication middleware correctly accepted all pre-crafted tokens and the
Supabase API responded without rate-limiting at any concurrency level.

*Load testing vs. stress testing — breaking point not found.*
Because no errors appeared and latency remained stable, the breaking point was
not reached within the tested range. A *stress test* would need to ramp users
beyond 100 to locate it — the primary candidate for the failure threshold is
Supabase's connection pool limit for the project's pricing tier.

==== *Conclusions*

|===
| Finding | Conclusion

| 0 % error rate at all load levels
| The authentication endpoints are stable within the tested load range.

| Average response time ~2 400–2 550 ms dominated by Supabase API calls
| Latency could be reduced by batching or caching the three sequential
  availability queries (e.g., a short-lived cache keyed on `doctor_id`).

| Throughput scales linearly with concurrency
| The Flask layer has significant headroom; optimisation should target
  the Supabase call chain rather than Flask routing.

| Breaking point not found within 100 users
| Stress testing beyond 100 users is recommended before any public launch
  to determine the Supabase connection-pool limit under real traffic.
|===
