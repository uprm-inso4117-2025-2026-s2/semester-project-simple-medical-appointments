==== Fuzz Testing Strategy for Appointment Scheduling
:author: Marymar Maldonado Roche

===== Overview

Fuzz testing (also called "fuzzing") is a testing technique in which the system is intentionally given unexpected, invalid, random, or extreme inputs to check whether it behaves safely. Instead of only feeding the system the "well-shaped" data that a normal user would enter, a fuzzer generates large numbers of strange or malformed values and observes how the program reacts.

The goal of fuzz testing is not to confirm that valid inputs produce valid results, but rather to confirm that *invalid inputs never cause the system to crash, hang, corrupt data, or behave in an undefined way*. A correct system should either accept the input, or reject it with a clear and predictable error.

For the Simple Medical Appointments project, the appointment scheduling feature is a natural target for fuzz testing because it accepts many different fields (dates, time ranges, durations, doctor IDs, clinic IDs, patient IDs, status flags, availability rules) and each one introduces an opportunity for invalid or malicious input.

===== Why Apply Fuzz Testing to Scheduling

Scheduling logic is one of the highest-risk areas of the system. A small bug in date or time handling can result in:

* Patients booking appointments that never happen
* Doctors being double-booked
* Appointments being silently created in the past
* The server crashing because a malformed value reached an unprotected piece of code

Traditional unit tests usually only check expected inputs ("a normal Tuesday at 10:00 AM"). Fuzz testing complements them by attacking the *unexpected* corners of the input space — exactly the kind of inputs that real users, broken frontends, or malicious clients eventually produce.

===== Connection to Lecture Concepts

Fuzz testing maps directly onto several core ideas introduced during lectures:

* *Input space:* Every parameter (date, time, duration, ID, status) defines a set of possible values. The full input space of the booking endpoint is the Cartesian product of all of those sets, which is too large to enumerate by hand. Fuzzing samples this enormous input space automatically.
* *Invalid cases:* Inputs that violate the format or type expected by the system (for example, the string `"banana"` placed in the `date` field, or `null` placed in `doctor_id`). A well-designed system rejects these cleanly.
* *Corner cases:* Values that sit on the boundary of valid and invalid (for example, an appointment that starts exactly at clinic closing time, or a duration of `0` minutes). These are classic sources of off-by-one defects.
* *Extreme cases:* Values that are technically of the right type but unusually large, unusually small, or otherwise improbable (for example, a duration of `1,000,000` minutes, the year `9999`, or a patient ID equal to the maximum signed 32-bit integer).

Fuzz testing exercises invalid, corner, and extreme cases as a normal part of its operation, which is something example-based testing rarely does.

===== Scheduling-Related Inputs to Fuzz

The scheduling subsystem of Simple Medical Appointments accepts the following fields, and each one should be fuzzed:

* *Appointment date* — calendar dates, including past dates, far-future dates, and malformed strings
* *Time ranges (start/end time)* — including end-before-start, identical start/end, and times outside `00:00–23:59`
* *Appointment duration* — including negative, zero, fractional, and very large values
* *Doctor ID* — including unknown IDs, negative IDs, non-numeric IDs, and IDs belonging to inactive accounts
* *Clinic ID* — same patterns as doctor ID
* *Patient ID* — same patterns, plus IDs for canceled or deleted patient profiles
* *Appointment status* — strings outside the allowed set (`scheduled`, `canceled`, `completed`, etc.) and case variations
* *Availability rules* — overlapping blocks, blocks outside working hours, and blocks with inverted ranges

The table below shows representative fuzz cases and the behavior the system must exhibit for each. The system should never crash, hang, or accept clearly invalid input silently.

In every row, the underlying requirement is the same: the server returns a controlled error response and keeps running. A crash, a 500-level error caused by an uncaught exception, or a successfully stored invalid appointment all count as fuzz-test failures.

===== Suggested Tools

For the Python/Flask backend of Simple Medical Appointments, suitable fuzzing tools include:

* *Hypothesis* — a property-based testing library that doubles as a structured fuzzer, generating random values within constrained strategies (dates, integers, strings, etc.)
* *atheris* — a coverage-guided fuzzer for Python, suitable for fuzzing parser-like functions such as the date and duration validators
* *schemathesis* — generates fuzzed HTTP requests directly from the OpenAPI schema of the REST endpoints

For the React/Vite frontend, lightweight property/fuzz tools like *fast-check* (with Vitest or Jest) can fuzz form inputs and ensure the client-side validation also rejects invalid data before it ever reaches the backend.

===== Benefits of Fuzz Testing the Scheduling Feature

* Exposes hidden defects in date, time, and duration handling
* Catches missing input validation before it reaches production
* Reduces the risk of crashes caused by malformed API requests
* Helps protect against injection-style attacks on ID fields
* Increases confidence that the scheduling endpoints are robust under unusual real-world conditions

===== Conclusion

Fuzz testing is a low-cost, high-coverage way to harden the appointment scheduling feature of Simple Medical Appointments. By systematically generating invalid, corner, and extreme inputs across the entire scheduling input space — dates, time ranges, durations, doctor/clinic/patient IDs, statuses, and availability rules — fuzzing forces the system to demonstrate that it fails *safely* when faced with unexpected data. Combined with the unit, property-based, and load tests already in place, fuzz testing closes the gap between "the system works for expected inputs" and "the system is resilient against all inputs".

==== Fuzzing Strategy Design for Appointment Scheduling Robustness
:author: Tasnim Said Khader

==== Introduction
The scheduling module contains some high-risk areas that could fail when exposed to malformed or unexpected data. The following robustness scenarios were identified based on the scheduling core functionality.

==== Conflict Detection and Resolution
Potential malformed inputs:

* Two appointments overlapping partially for the same doctor.
* Two appointments overlapping completely.
* Appointment ending before it starts.
* Appointment scheduled outside clinic availability.
* Appointment scheduled during blocked clinic hours.
* Appointment duration set to negative values.

Expected system behavior:

* Reject overlapping appointments.
* Reject invalid time ranges.
* Reject appointments violating clinic scheduling rules.

Example fuzzing input:
[source,json]
----
{
  "doctor_id": 7,
  "date": "2026-03-12",
  "start_time": "2:00 PM",
  "end_time": "1:00 PM"
}
----

Expected result:

*Validation Error:* Appointment end time cannot occur before start time.

==== Capacity Handling
Potential malformed inputs:

* Negative slot capacity.
* Capacity values exceeding realistic limits.
* Appointment booking after capacity is reached.
* Duplicate bookings for the same slot.

Example fuzzing inputs:
[source,json]
----
{
  "slot_capacity": -3
}
----

[source,json]
----
{
  "slot_capacity": 10000
}
----

Expected system behavior:

* Reject invalid capacity values.
* Prevent overbooking once capacity is reached.

==== Waitlist Logic
Potential malformed inputs:

* Same patient added multiple times to waitlist
* Waitlist request for unavailable doctor
* Automatic reassignment triggered with no waitlist entries
* Cancellation event attempting to assign a removed patient

Example fuzzing input:
[source,json]
----
{
  "patient_id": 15,
  "doctor_id": 4,
  "waitlist_entries": 3
}
----

Expected system behavior:

* Prevent duplicate waitlist entries.
* Preserve fair ordering of patients.

==== Patient Scheduling from Submission
Potential malformed inputs:

* Missing doctor selection.
* Missing clinic selection.
* Null appointment date.
* Invalid dates.
* Extremely long patient notes.
* Incorrect data types.

Example fuzzing inputs:
[source,json]
----
{
  "doctor_id": null,
  "clinic_id": 12,
  "appointment_date": "2026-02-30"
}
----

[source,json]
----
{
  "doctor_id": "Cardiology",
  "duration": "two hours"
}
----

Expected system behavior:

* Reject incomplete or malformed submissions.
* Return clear validation messages to the patient.

==== Robustness Risks Identified
Based on the scheduling workflow, the following risks were identified:

* Incorrect overlap detection may result in double-booking.
* Capacity failures may lead to overbooking.
* Invalid dates or times could break scheduling generation logic.
* Duplicate waitlist entries could create unfair scheduling.
* Missing patient or doctor data may create incomplete appointments.
* Simultaneous booking attempts could result in race conditions.

==== Validation Improvements Proposed
1. *Time Validation Layer*

    Before processing appointments, validate:

    * Start time occurs before end time
    * Appointment falls within clinic hours
    * Appointment does not violate blocked schedules

2. *Strict Input Validation*

    Patient scheduling forms should require:

    * Valid clinic ID,
    * Valid doctor ID,
    * Correct date formatting,
    * Required fields completed

    before scheduling requests are processed.

3. *Capacity Protection Rules*

    The system should:

    * Reject negative capacity values
    * Limit maximum appointments per slot
    * Prevent duplicate bookings

4. *Waitlist Integrity Checks*

    The system should:
    
    * Prevent duplicate waitlist entries
    * Preserve patient queue order
    * Trigger reassignment only after confirmed cancellation

==== Future Fuzzing Execution Plan

Once Flask endpoints are implemented, fuzz testing will be executed by:

* Generating semi-random malformed scheduling inputs.
* Automatically submitting data to scheduling endpoints.
* Monitoring for:
    - crashes
    - unhandled exceptions
    - incorrect booking behavior
    - invalid appointment creation

=== [.added]#Fuzzing the Web Interface with Hypothesis (base-code branch)#

The project implements structured fuzzing of the Flask web interface using Hypothesis as a coverage-guided generator, following the property-based/fuzzing approach from the fuzzing book. These tests are in `base-code` and run with `hypothesis>=6.100.0`.

==== [.added]#API-Level Fuzzing: POST /api/auth/register#

`backend/tests/test_user_management_properties.py` (PROP-3) fuzzes the live registration endpoint by generating arbitrary strings as the `role` field and verifying the server always returns HTTP 400 for any invalid role. This is web-interface fuzzing: Hypothesis sends generated inputs through the Flask test client and checks the server never crashes or accepts invalid data.

[source,python]
----
@given(role=st.text())
@settings(max_examples=100, suppress_health_check=[HealthCheck.function_scoped_fixture])
def test_invalid_role_always_returns_400(client, role):
    assume(role not in VALID_ROLES)
    response = client.post("/api/auth/register", json=_full_payload(role=role))
    assert response.status_code == 400
----

Hypothesis generates 100 random strings per run, including Unicode sequences, empty strings, SQL-injection fragments, and whitespace-only values — the same categories a dedicated web fuzzer would target.

==== [.added]#Stateful Fuzzing: Booking Machine#

`backend/tests/test_pbt_shrinking_classification.py` implements a `RuleBasedStateMachine` that generates random sequences of book, cancel, and query operations against the scheduling logic. This is the stateful model-based fuzzing approach described in the "Testing Web Applications" chapter of the fuzzing book: the machine explores sequences of interactions rather than individual inputs, and Hypothesis shrinks any failing sequence to its minimal reproducing form.

==== [.added]#Structured Input Fuzzing: Scheduling Properties#

`backend/tests/test_pbt_filter_conflicting_slots.py` and `test_pbt_shrinking_classification.py` generate hundreds of random `(date, time, slot_minutes)` combinations and feed them to the scheduling logic, verifying that the system never returns conflicting slots or crashes on unexpected input combinations. This is the structured fuzzing strategy from the fuzzing book applied to the scheduling domain.

Run all fuzzing-related tests:
[source,bash]
----
cd backend && pytest tests/test_user_management_properties.py \
               tests/test_pbt_filter_conflicting_slots.py \
               tests/test_pbt_shrinking_classification.py -v -s
----
