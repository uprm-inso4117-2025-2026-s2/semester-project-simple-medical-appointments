[.changed]#Each executable scenario is written in Given-When-Then form and validated by step definitions that assert concrete state transitions (`Requested`, `Confirmed`, `Cancelled`) and slot availability effects.#

===== *Scenario Completeness Correction: Insurance Approval Flow*

[.changed]#Previous narrative versions implied immediate confirmation for all booking requests. That is incomplete for appointments requiring referral/insurance prerequisites.#

[.added]#Design correction: booking can end in `PendingApproval` when prerequisites are missing, and only transitions to `Confirmed` after prerequisite evidence is recorded (see <<REQ-CONFIRM-F-01>>, <<REQ-CONFIRM-F-02>>, <<REQ-CONFIRM-F-03>>).#

[.added]#This flow is currently modeled in Section 3.2 validation scenarios and is a planned BDD expansion item (not yet executable in `appointment_booking.feature`).#

===== *Scenario 2 Boundary Question (\"5 till 2 p.m.\")*

[.changed]#The rescheduling boundary case (for example request submitted at 1:55 PM for a 2:00 PM appointment) is not covered by current executable BDD scenarios.#

[.added]#Planned scenario design:#

----
Given Lucia has a Confirmed Appointment at 2:00 PM
  And clinic policy requires minimum reschedule notice
When Lucia requests reschedule at 1:55 PM
Then the system rejects or accepts the request according to configured policy
  And the decision is recorded with explicit reason
----

[.added]#This planned case is tied to <<REQ-BOOK-F-03>> (clinic-defined cancellation/rescheduling policy windows).#
