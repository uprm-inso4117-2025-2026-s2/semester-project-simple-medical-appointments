==== *Core Domain Entities*

[.changed]#Entities are defined in Section 2.1.2. This subsection shows why they appear in the model.#

*Patient* - derived from repeated booking initiation behavior across clinics.

*Provider* - derived from constrained multi-clinic availability patterns.

*Clinic* - derived from organizational scheduling boundaries.

*Appointment* - derived from requirement for confirmed scheduled interactions.

*TimeSlot* - derived from structured provider availability segmentation.

*Referral* - derived from prerequisite consultation constraints.

*InsuranceAuthorization* - derived from external validation requirements.

==== *Event Derivation (State Transitions Only)*

[IMPORTANT]
[.changed]#An event is instantaneous. It is not an action or process.#

The following events are derived from stakeholder fragments and requirements:

* AppointmentRequestSubmitted  
  -> Derived from repeated patient request attempts (Section 1.3.1)  
  -> Represents transition where a request record is created

* AppointmentConfirmed  
  -> Derived from confirmation requirements (<<REQ-CONFIRM-F-02>>)  
  -> Represents transition into `Confirmed` appointment status

* AppointmentCancelled  
  -> Derived from cancellation handling patterns (Section 1.3.1, <<REQ-BOOK-F-02>>)  
  -> Represents transition where appointment is cancelled and slot can be released

* NoShowRecorded  
  -> Derived from attendance outcome requirement (<<REQ-ATTEND-F-01>>)  
  -> Represents transition where unattended confirmed appointment is recorded

* InsuranceAuthorizationReceived  
  -> Derived from prerequisite evidence requirement (<<REQ-CONFIRM-F-03>>)  
  -> Represents transition where required external approval is recorded

* WaitlistEntryCreated  
  -> Derived from waitlist requirements (<<REQ-WAIT-F-01>>)  
  -> Represents transition where patient joins waitlist

* ReminderSent  
  -> Derived from reminder requirement (<<REQ-NOTIF-F-02>>)  
  -> Represents transition where reminder dispatch is recorded

==== *Behavioral Abstraction (Event Composition)*

[.changed]#Behaviors are modeled as composed event sequences, not isolated labels.#

* Multi-clinic booking behavior  
  -> AppointmentRequestSubmitted -> (AppointmentConfirmed or rejection)

* Cancellation-driven reassignment behavior  
  -> AppointmentCancelled -> slot available -> waitlist selection opportunity

* Authorization-constrained booking behavior  
  -> AppointmentRequestSubmitted -> InsuranceAuthorizationReceived -> AppointmentConfirmed

* Attendance outcome behavior  
  -> AppointmentConfirmed -> (Completed or NoShowRecorded)

==== *Operational Concepts (System-Level Properties)*

[.changed]#Operational concepts represent emergent system properties derived from repeated constraints.#

*Availability Visibility* - derived from fragmented calendar access.

*Scheduling Coordination Load* - derived from manual coordination workflows.

*Waiting Time* - derived from delays between request and confirmation.

*No-Show Rate* - derived from unattended appointment frequency.

*Access Inequality* - derived from differences in booking success across users.

==== *Concept Relationships (Domain Structure)*

[.changed]#Relationships describe structural coupling among entities and states.#

* A Patient submits an appointment request.
* A Provider publishes TimeSlots within a Clinic context.
* An Appointment binds one Patient, one Provider, one Clinic, and one TimeSlot.
* Cancellation transitions an Appointment and releases its TimeSlot state.
* Referral and InsuranceAuthorization constrain appointment confirmation.
* Reminder notifications are associated with confirmed appointments.
