
==== *Formal Verification (Hoare Logic / Weakest Preconditions)*


The function selected for formal verification is the scheduling operation `book_appointment(patient_id, doctor_id, slot_id)`. This operation is a meaningful verification target because it transforms an available medical time slot into a confirmed reservation while preserving the scheduling constraint that double booking must not occur.


The verification is applied at the level of the project’s booking logic as defined by the scheduling requirements and domain rules. This is appropriate because the correctness of the booking operation depends primarily on the preservation of its state constraints rather than on framework-specific implementation details.


===== *Hoare Triple*

[source,text]
----
{ P } book_appointment(patient_id, doctor_id, slot_id) { Q }
----


Where `P` and `Q` are defined as follows.

===== *Predicate Relationship (`booked` vs `slotAvailable`)*

[.changed]#To avoid ambiguity, `booked(doctor_id, slot_id)` is treated as a derived predicate, not an independent flag.#

[source,text]
----
booked(doctor_id, slot_id) ≜
  exists appointment a :
    hasDoctor(a, doctor_id) and
    hasSlot(a, slot_id) and
    status(a) = Confirmed
----

[.changed]#For the same doctor-slot pair, the model enforces a consistency rule:#

[source,text]
----
slotAvailable(slot_id)  <=>  not booked(doctor_id, slot_id)
----

[.changed]#So yes: one can be expressed in terms of the other, provided the scope is the same slot and doctor pair and status semantics are fixed to `Confirmed` as the consuming state.#


===== *Preconditions*


* `patientExists(patient_id)`
* `doctorExists(doctor_id)`
* `slotExists(slot_id)`
* `slotBelongsToDoctor(slot_id, doctor_id)`
* `slotAvailable(slot_id)`
* `not booked(doctor_id, slot_id)` (equivalently, `slotAvailable(slot_id)`)


===== *Postconditions*


* `booked(doctor_id, slot_id)`
* `not slotAvailable(slot_id)`
* `exists appointment a such that hasPatient(a, patient_id) and hasDoctor(a, doctor_id) and hasSlot(a, slot_id)`
* No unrelated appointment or slot is modified


===== *Invariants Preserved*


* At most one confirmed appointment may exist for a given doctor-slot pair.
* A slot that is booked for the verified doctor-slot pair is no longer available.
* State outside the target booking remains unchanged.


These properties capture the main safety objective of the project’s scheduling logic: a successful reservation consumes exactly one valid slot and cannot introduce double booking as a side effect.


===== *Weakest-Precondition Reasoning*


To make the proof explicit, the state-changing core of the operation can be abstracted as:

[source,text]
----
assert slotAvailable(slot_id);
assert not booked(doctor_id, slot_id);
booked(doctor_id, slot_id) := true;
slotAvailable(slot_id) := false;
----


Let the desired postcondition be:

[source,text]
----
Q = booked(doctor_id, slot_id) and not slotAvailable(slot_id)
----


Computing the weakest precondition backwards gives:

[source,text]
----
wp(slotAvailable(slot_id) := false, Q)
  = booked(doctor_id, slot_id)

wp(booked(doctor_id, slot_id) := true;
   slotAvailable(slot_id) := false, Q)
  = true

wp(assert not booked(doctor_id, slot_id);
   booked(doctor_id, slot_id) := true;
   slotAvailable(slot_id) := false, Q)
  = not booked(doctor_id, slot_id)

wp(assert slotAvailable(slot_id);
   assert not booked(doctor_id, slot_id);
   booked(doctor_id, slot_id) := true;
   slotAvailable(slot_id) := false, Q)
  = slotAvailable(slot_id) and not booked(doctor_id, slot_id)
----


Therefore, the weakest precondition for reaching `Q` is exactly that the slot is available and not already booked before the state transition begins. This matches the intended scheduling rule for the project.

[.added]#Because `booked` is defined from appointment status and slot association, this weakest precondition can also be written with a single availability condition under the same consistency rule.#


===== *Verification Result*


Under the Hoare triple `{P} book_appointment(patient_id, doctor_id, slot_id) {Q}`, the proof shows that if all preconditions hold, execution establishes the required booking state and preserves the invariant against double booking. If any precondition fails, the operation must reject the request and leave the system state unchanged.


===== *Implications for System Correctness*


This verification is important because the booking operation is safety-critical in the medical scheduling domain. The proof establishes that the operation may succeed only from a valid scheduling state and that a successful execution immediately makes the selected slot unavailable. In practical terms, this prevents one of the most serious scheduling errors in the system: assigning the same provider and time slot to more than one appointment.
