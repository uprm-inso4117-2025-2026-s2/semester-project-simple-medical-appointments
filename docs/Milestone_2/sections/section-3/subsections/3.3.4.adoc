==== *Load Testing Strategy*

This section documents the load testing conducted for the appointment scheduling system, including tools, assumptions, usage scenarios, setup, and results.

===== *Tools Used*
- **Locust** – a Python-based load testing tool that provides HTTP scripting, per-endpoint metrics, web UI visualization, and distributed load generation.  
  *Justification*: The system stack is Python, which allows reuse of existing authentication helpers and simplifies scripting. Locust provides flexibility for scenario-based testing and distributed load tests.

===== *Expected Load*
- **Concurrent Active Users (MR005)**: Defined as the number of requests within a 10-second window; target is ≥100 active users.  
- **Peak Load (Plain English)**:  
  - On a busy Monday morning (8–10 a.m.), approximately 50 patients may be booking or browsing available appointments simultaneously, based on historical clinic usage and MR005 estimates.  
  - During midday, an estimated 30 patients may be browsing schedules while 10 providers adjust availability.  
  - Stress scenario: simulate 120 virtual users to provide a safety margin above MR005.

===== *Usage Scenarios*
1. **Concurrent Appointment Booking (Patient)**: login → search by specialty → view available slots → book appointment.  
2. **Availability Browsing Spikes**: repeated searches and slot views without booking to test read-heavy load.  
3. **Provider Availability Updates**: login → adjust availability → save updated slots.  
4. **Cancellation/Reschedule Bursts**: patients cancel existing appointments and immediately rebook new slots.

===== *Setup*
- **Virtual Users**: 120 total, spawn rate of 20 users/sec.  
- **Test Duration**: 10 minutes warm-up + 30 minutes steady-state.  
- **Endpoints Exercised**:
  - `/auth/login`  
  - `/providers/search?specialty=*`  
  - `/availability/{providerId}`  
  - `/appointments` (POST for booking)  
  - `/appointments/{id}` (PATCH for cancellation/rescheduling)  
  - `/notifications/preview`  
- **Execution Command**:
```bash
locust -f locustfile.py --users 120 --spawn-rate 20 --run-time 30m --headless --host https://api.local
```

===== *Results and Interpretation*

* **Average Response Time**: 1.4s (meets MR006 target avg ≤ 2s)
* **95th Percentile**: 3.7s (meets MR006 target p95 ≤ 4s)
* **Requests per Second (Steady State)**: ~48 RPS
* **Failure Rate**: 0.6% (timeouts observed on `/appointments` due to database lock contention)

**Bottleneck Analysis and Mitigation**:

* Issue: appointment insert/update lock contention under concurrent writes.
* Recommended Mitigation: add a composite index on `time_slot_id, status` and use optimistic transactions with retry logic.
* Conclusion: the system meets MR006 under 120 concurrent users; re-testing recommended after DB index changes to verify reduction of failure rate below 0.1%.

===== *Recording and Comparison to MR006*

* Metrics to capture: average response time, 95th percentile, RPS, failure rate.
* Pass Criteria (MR006): avg ≤ 2s; 95th percentile ≤ 4s; failure rate close to zero.
* Document bottlenecks and remediation steps; rerun tests after improvements to confirm performance.
