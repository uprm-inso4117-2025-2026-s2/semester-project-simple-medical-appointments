function authenticate(request):
    credentials = extract(request.body, ["email", "password"])

    if not credentials.valid():
        return Response(400, "Missing or malformed credentials")

    user = UserRepository.findByEmail(credentials.email)

    if user is null or not hash.verify(credentials.password, user.passwordHash):
        return Response(401, "Invalid email or password")

    token = JWT.sign(payload={ userId: user.id, role: user.role },
                     secret=ENV.JWT_SECRET,
                     expiresIn="2h")

    return Response(200, { token: token })

===== [.removed]#Input Validation Strategy#

[.removed]#Another decision worth illustrating is how the application handles input validation. Rather than scattering validation logic across handlers, the design calls for a dedicated validation layer that intercepts requests before they reach business logic:#

[.removed]
[source,text]
----
function validate(schema, request):
    errors = []

    for each field in schema:
        value = request.body[field.name]

        if field.required and value is null:
            errors.append({ field: field.name, issue: "required" })
            continue

        if not field.type.matches(value):
            errors.append({ field: field.name, issue: "invalid type" })

    if errors is not empty:
        return Response(422, { errors: errors })

    return next(request)
----

===== [.added]#Application Initialization and Structure#

[.added]#The backend is initialized using an application factory pattern, implemented in `backend/app/__init__.py`.#

[.added]
[source,python]
----
def create_app(testing: bool = False):
    app = Flask(__name__)

    app.config.from_object(Config)
    if testing:
        app.config["TESTING"] = True

    CORS(app)
    init_supabase(app)
    register_routes(app)

    return app
----

 [.added]#This pattern allows the application to be created in a controlled and flexible way. Instead of relying on global initialization, the system builds the application step by step. Configuration is loaded first, followed by external service initialization and route registration.#

[.added]#This separation is important because it allows different environments to be handled cleanly. For example, when running tests, the application can disable external integrations such as Supabase. It also makes the system easier to maintain, since each responsibility is clearly defined and isolated.#

===== [.added]#Supabase Integration#

[.added]#The system integrates with Supabase for authentication and data storage. This integration is centralized in `backend/app/supabase.py`.#

[.added]
[source,python]
----
def init_supabase(app):
    global supabase

    if app.config.get("TESTING"):
        supabase = None
        app.supabase = None
        return None

    url = app.config.get('SUPABASE_URL')
    key = app.config.get('SUPABASE_KEY')

    if not url or not key:
        raise RuntimeError('Supabase environment variables are missing.')

    supabase = create_client(url, key)
    app.supabase = supabase
    return supabase
----

[.added]#By initializing the client once and attaching it to the application, the system avoids duplicating configuration logic across different components.#

[.added]#An important detail is the conditional behavior during testing. When the application runs in testing mode, the Supabase client is disabled. This prevents external dependencies from affecting test execution and ensures that tests remain fast and reliable.#

===== [.added]#Authentication and Authorization#

[.added]#Authentication and authorization are handled as separate steps, both implemented in `backend/app/routes/profile.py`.#

[.added]
[source,python]
----
status, user_response, _ = _supabase_request('GET', '/auth/v1/user', user_token=token)

role_status, role_response, _ = _supabase_request(
    'GET',
    '/rest/v1/user_roles',
    query={'user_id': f'eq.{user_id}', 'select': 'roles(name)'},
)
----

[.added]#The system first verifies the identity of the user using a token. Once the user is authenticated, a second query retrieves the user’s role.#

[.added]#This separation is intentional. Authentication answers the question “who is the user?”, while authorization answers “what is the user allowed to do?”. Keeping these concerns independent makes the system more flexible and easier to evolve as role definitions change.#
