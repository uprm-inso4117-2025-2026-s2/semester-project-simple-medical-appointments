[NOTE]
====

== Domain actors, entities, and core concepts

Patient :: `[domain] [actor]`
A person seeking medical consultation or treatment. A Patient may request, confirm, cancel, or reschedule appointments and may join a waitlist when no acceptable times are available.

Caregiver :: `[domain] [actor]`
A person who manages or coordinates appointments on behalf of a Patient who cannot coordinate independently.

Doctor :: `[domain] [actor]`
A licensed medical professional who provides consultations and whose availability is scheduled through time slots at one or more clinics.
+
Deprecated aliases: “Provider”, “Healthcare Provider” (replace these with Doctor across the document).

Specialty :: `[domain] [taxonomy]` _(required missing term)_
A classification of a Doctor’s practice area (e.g., cardiology, general practice) used to match patients to appropriate doctors.

Clinic :: `[domain] [entity]`
A healthcare facility/location that schedules appointments with Doctors and operates within defined operational hours.

Appointment :: `[domain] [entity]`
A reserved time commitment for a Patient to consult a Doctor at a Clinic, associated with a consultation type and a booking status.

Time Slot :: `[domain] [entity]`
A discrete reservable interval in a Doctor’s schedule. A time slot may be available, reserved, canceled/released, or expired.

TimeSlotCatalog :: `[domain] [collection]` _(required missing term)_
The collection of time slots that represents published availability. (Scope must be made clear elsewhere: per-doctor vs per-clinic catalog.)

Schedule :: `[domain] [entity]`
The structured allocation of time slots and appointments associated with a Doctor and/or Clinic.

Consultation Type :: `[domain] [taxonomy]`
A classification of medical visit (e.g., first-time visit, follow-up, procedure) that influences planning assumptions (like expected duration) and may introduce constraints (e.g., authorization required).

Waitlist :: `[domain] [entity]`
An ordered collection of waiting patients when no acceptable time slots are available.

Cancellation :: `[domain] [event]`
The release of a previously reserved appointment before its scheduled time.

No-Show :: `[domain] [event]`
The absence of a patient at a scheduled appointment without prior cancellation.

Insurance Authorization :: `[domain] [process/entity]`
An external approval outcome required before certain appointments can be confirmed for specific consultation types.

Referral :: `[domain] [entity]`
A directive indicating that a patient must meet referral conditions before certain consultations can be confirmed.

Availability :: `[domain] [state]`
The state of a time slot being open (or not) for reservation.

Booking Status :: `[domain] [state]`
The state of an appointment (e.g., pending, confirmed, canceled, completed).

Operational Hours :: `[domain] [constraint-entity/value]`
The time boundaries within which a clinic accepts or schedules appointments.

AppointmentBook :: `[domain] [collection]` _(required missing term)_
The collection of scheduled appointments used as the official record of bookings (and used to detect scheduling conflicts).

ClinicSystem :: `[requirements] [system]` _(required missing term)_
The system-to-be boundary referenced in requirements and function signatures: the scheduling system that maintains doctors, clinics, time slots, appointment booking, and related constraints.

BehaviorTrace :: `[requirements] [artifact]` _(required missing term)_
A trace/log of domain-relevant actions/events (e.g., request made, slot offered, appointment confirmed/canceled) used for accountability and analysis.

== Domain actions (high-level names only)

Request Appointment :: `[domain] [action]`
A Patient expresses intent to reserve an available time slot.

Reserve Time Slot :: `[domain] [action]`
The act of assigning a specific time slot to a Patient (creating or updating an appointment record).

Confirm Appointment :: `[domain] [action]`
The act of transitioning an appointment from pending to confirmed, once required conditions are satisfied.

Cancel Appointment :: `[domain] [action]`
The act of canceling an appointment, releasing the reserved time slot back to availability.

Reschedule Appointment :: `[domain] [action]`
The act of replacing one reserved time slot with another for an existing appointment.

Join Waitlist :: `[domain] [action]`
A Patient registers interest in being assigned a slot if one becomes available.

Assign Waitlisted Patient :: `[domain] [action/behavior]`
The allocation workflow triggered by a newly freed time slot (often includes contacting the next eligible patient and updating the appointment status).

Authorize Coverage :: `[domain] [external event]`
An external authorization outcome is received (approved/denied), affecting whether an appointment can be confirmed.

Expire Slot :: `[domain] [event]`
A held or unconfirmed slot is released automatically after a confirmation window ends.

== Domain constraints (invariants)

No Double Booking :: `[domain] [constraint]`
A single time slot must not be reserved by more than one patient simultaneously (unless the project explicitly defines capacity > 1 elsewhere).

Single Active Appointment per Doctor Constraint :: `[domain] [constraint]` _(reinterpreted to avoid overly strict rule)_
A patient may not hold overlapping active appointments with the same Doctor.
+
(Important clarification: this does not forbid multiple future appointments with the same Doctor on different days.)

Operational Hour Restriction :: `[domain] [constraint]`
Appointments cannot be scheduled outside clinic operational hours.

Consultation Duration Integrity :: `[domain] [constraint]` _(updated for duration uncertainty)_
Time slots are planned using an expected duration for the consultation type; actual visit length may vary, so the domain does not require exact duration matching in real-world execution.

Waitlist Ordering Integrity :: `[domain] [constraint]`
Waitlisted patients must be prioritized and assigned according to the defined ordering rule.

Authorization Dependency :: `[domain] [constraint]`
Certain appointment types cannot transition to confirmed status until required insurance authorization is obtained.

== Observed domain phenomena

Call saturation :: `[domain] [phenomenon]`
High call congestion during clinic opening hours makes scheduling access difficult.

Appointment delay :: `[domain] [phenomenon]`
Long waiting periods for non-urgent care (e.g., months until first available slot).

Manual reminder artifact :: `[domain] [phenomenon]`
Patients rely on paper/manual reminders to avoid forgetting appointments.

Office-hour constraint :: `[domain] [phenomenon]`
Scheduling is hard for patients who cannot call during clinic office hours.

Waitlist opacity :: `[domain] [phenomenon]`
Patients cannot see waitlist progress or status, causing uncertainty.

Schedule fragmentation :: `[domain] [phenomenon]`
Clinics lack visibility into other clinic locations’ schedules; availability is siloed.

Consultation variability :: `[domain] [phenomenon]`
Consultations can take longer than expected, shifting the schedule.

No-show fluctuation :: `[domain] [phenomenon]`
No-shows occur unpredictably, affecting schedule efficiency.

Defensive reservation :: `[domain] [phenomenon]`
Some patients book multiple appointments “just in case,” then cancel later, disrupting planning.

External system latency :: `[domain] [phenomenon]`
Insurance authorization processes introduce delays because they depend on external systems.

== Cross-phase (non-domain) technical terms

User Account :: `[implementation] [entity]`
A technical authentication construct representing a system login identity (not a domain concept).

Authentication Token :: `[implementation] [artifact]`
A signed credential used to verify session identity (not a domain concept).

Session :: `[implementation] [state]`
Authenticated runtime context allowing authorized actions (not a domain concept).

Notification :: `[requirements] [artifact]`
A system-generated message informing stakeholders about appointment changes (system-to-be concern).
