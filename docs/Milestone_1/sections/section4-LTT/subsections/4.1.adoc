=== *Testing Concepts*


==== Defining Acceptance Testing
:author: Jorge Peralta

===== Overview

This document will define clear and measurable acceptance criteria that determine when the Simple Medical Appointments system is ready for deployment in a clinical environment. The goal is to verify that the system fulfills its intended purpose and satisfies stakeholder expectations before release. In this cases the question is, "Is the system ready for clinical use?".

===== Scope of Acceptance Testing

Acceptance testing will evaluate the system from a clinic-level perspective, focusing on:

* Patient Booking Workflow
* Provider Schedule Management
* Conflict prevention (double-booking)
* Data integrity and protection
* Usability for staff and patients

===== Acceptance Criteria

====== Functional Acceptance Criteria

[cols="1,3,3,3,1", options="header"]
|===
| ID | Criterion | Measurement | Verification Method | Priority

| F1
| No double bookings
| 0 overlapping appointments for same provider/time
| Create conflicting bookings intentionally
| Critical

| F2
| Appointment confirmation generated
| Confirmation message and ID generated in 100% of successful bookings
| Execute booking workflow
| Critical

| F3
| Cancellation updates schedule
| Cancelled slot becomes immediately available
| Cancel appointment and verify slot
| High

| F4
| Provider schedule displays correctly
| 100% of booked slots reflected accurately
| Cross-check database vs UI
| High
|===

====== Reliability Criteria

[cols="1,3,3,3,1", options="header"]
|===
| ID | Criterion | Measurement | Verification Method | Priority

| R1
| No data loss during booking
| 100% persistence of confirmed appointments
| Database validation
| Critical

| R2
| System stability during peak use
| No crash during 1-hour simulated use
| Session based stress testing
| High
|===

====== Security Criteria

[cols="1,3,3,3,1", options="header"]
|===
| ID | Criterion | Measurement | Verification Method | Priority

| S1
| Unauthorized access blocked
| Non-authenticated users cannot view appointment data
| Access control testing
| Critical

| S2
| Role-based access enforced
| Patients cannot modify provider schedules
| Role-based testing
| Critical

| S3
| Sensitive data protected
| Appointment details not exposed via URL manipulation
| URL tampering tests
| High
|===

====== Usability Criteria

[cols="1,3,3,3,1", options="header"]
|===
| ID | Criterion | Measurement | Verification Method | Priority

| U1
| Staff schedule modification time
| New user completes booking in ≤ 3 minutes
| Timed usability test
| High

| U2
| Staff schedule modification time
| Staff edits appointment in ≤ 1 minute
| Timed workflow test
| High

| U3
| Error clarity
| Invalid inputs generate clear, actionable message
| Input invalid data
| Medium
|===

===== Deployment Approval Rule

The system will only be approved for deployment if:

. All critical criteria pass.
. At least 90% of high criteria pass.
. No unresolved defects exist in core booking functionality.
. No open security vulnerabilities affecting patient data.
