=== *Test Planning*

==== Risk-Based Test Planning Optimization
:author: Segmar Rosado

===== Objective

Research risk-based test planning in software reliability engineering, focusing on how testing activities are prioritized using expected defect cost modeling and constrained resource allocation.

===== Introduction

Software testing operates under strict limitations in time, personnel, and budget. Exhaustive testing of all possible inputs, configurations, and system states is infeasible in practical environments. As a result, test planning must be strategic and risk-driven. Risk-based test planning provides a structured approach to allocating limited testing resources toward areas that present the highest expected impact on system reliability.

===== Expected Defect Cost Model

At the core of risk-based testing lies the expected defect cost equation:

Expected Cost(D) = P(D occurs) × Cost(D occurs)

Where:

* P(D occurs) represents the probability that a defect exists in a given component or feature.
* Cost(D occurs) represents the impact or severity if that defect manifests in production.

This model transforms test prioritization into a quantitative decision-making process. Rather than distributing effort evenly, testing focuses first on components with the highest expected loss. Indicators that may increase defect probability include system complexity, synchronization and timing issues, high user interaction (e.g., GUI-heavy components), and inexperienced development. Indicators that increase defect impact include essential functionality, safety-critical behavior, reputational damage, and frequent user-facing failures.

By combining probability and impact, the model provides a rational framework for determining which tests should be executed first.

===== Multi-Axis Test Plan Decomposition

Risk-based planning requires structured decomposition of the system under test. A comprehensive test plan unfolds across multiple axes, including:

* Testing Level (Unit, Integration, System, Acceptance)
* Testing Type (Functional, Security, Performance, Usability)
* Input Space (common, corner, extreme, invalid cases)
* Platform and Environment
* Configuration
* Load and Performance Conditions
* UI Elements and Interaction Paths

This multi-dimensional structure ensures coverage is systematic rather than arbitrary. Instead of viewing the system as a flat list of test cases, it is represented as a hierarchical tree. The root represents the entire system, and branches represent decomposition along selected axes. Each leaf eventually corresponds to an individual test case.

This approach enables targeted prioritization within each axis while maintaining traceability and logical organization.

===== Budget-Constrained Prioritization and Pruning

Because resources are finite, not all identified test cases can be executed. Risk-based test planning incorporates prioritization and pruning to ensure that execution remains within budget constraints.

The planning process typically follows these steps:

. Define an overall test strategy.
. Decompose the system along a selected axis.
. Estimate time and effort required for candidate tests.
. Rank tests according to expected defect cost.
. Remove lower-priority tests until the total effort fits within available resources.
. Repeat decomposition for higher-risk branches.

This transforms testing into a constrained optimization problem. The objective is not maximum coverage, but maximum risk reduction per unit of effort.

Additionally, the Law of Diminishing Returns applies to defect detection. Early testing phases tend to uncover many defects quickly, while later phases yield progressively fewer new findings. Recognizing this reliability growth behavior informs stopping decisions and prevents inefficient over-testing.

===== Discussion

Risk-based test planning aligns software reliability engineering with economic reasoning. It acknowledges uncertainty in defect presence and quantifies decision-making using expected impact. By structuring tests along multiple axes and systematically pruning lower-value activities, the approach ensures that limited resources are directed toward areas of highest risk exposure.

This method strengthens reliability not through exhaustive verification, but through disciplined prioritization and strategic allocation of effort.

===== Conclusion

Risk-based test planning reframes software testing as a rational, risk-informed optimization process. By applying the expected defect cost model, decomposing the system across structured axes, and pruning tests to remain within budget constraints, testing becomes both economically justified and technically disciplined. This approach maximizes reliability improvement under practical development constraints and will be used and expanded upon in this project.

===== Risk Model

====== Prioritization Formula

Because resources are limited and it is impossible to test every possible situation, testing effort must be invested wisely. The goal is to deliver the right tests, in the right order, to discover as many issues as time and budget allow [1]. Prioritization is based on the expected cost of each defect:

____
*D = P(D occurs) × Cost(D occurs)* [1]
____

Tests targeting the highest D values are executed first.

====== What Raises Probability

The following conditions increase the likelihood that a defect exists in a given area [1]:

- Complex units
- High user involvement through GUIs
- Synchronization and timing issues
- Inexperienced developers

For this module, role-permission logic and session state management represent the primary complexity. Login and registration involve heavy form-based user interaction, which further raises P(D).

====== What Raises Cost

The following conditions increase the impact of a defect reaching production [1]:

- *Sine qua non functionality* -- authentication is the prerequisite for every other system feature
- *Damage to reputation and trust* -- unauthorized access to patient or provider data in a healthcare system
- *Frequent or annoying defects* -- login and registration are the most exercised flows in the system

====== TC-01: Patient URL Manipulation to Admin Route

[cols="1,3", options="header"]
|===
| Field | Detail

| Test ID
| TC-01

| Title
| Patient-role user attempts direct URL navigation to an Admin-only route

| Linked Risk
| RISK-01 (D = 25)

| Testing Type
| Security

| Axes Covered
| Functionality, UI Elements

| Input Partition
| Corner -- valid authenticated session, invalid route for role
|===

*Preconditions:* +
A Patient-role account is authenticated. At least one Admin-only route exists.

*Steps:*

- Authenticate as a Patient and obtain a valid session token.
- Manually enter the Admin-designated route URL in the browser address bar.
- Observe the HTTP response and UI behavior.
- Repeat using the Doctor-designated route.
- Using a REST client, send a direct API request to the Admin route with the Patient token in the Authorization header.
- Observe the API response.

*Expected Result:* +
Browser navigation returns HTTP 403 or redirects to an unauthorized page. No Admin or Doctor content is rendered. The Patient session remains active. Direct API call also returns HTTP 403 with no data.

*Failure Condition:* Any protected content renders, or the API returns HTTP 200 with data.

====== TC-07: Password Reset Token Reuse and Expiry

[cols="1,3", options="header"]
|===
| Field | Detail

| Test ID
| TC-07

| Title
| Previously used or expired password reset token submitted again

| Linked Risk
| RISK-07 (D = 15)

| Testing Type
| Functional, Security

| Axes Covered
| Functionality, Input Space

| Input Partition
| Invalid (reuse); Extreme (expiry)
|===

*Preconditions:* +
A password reset flow exists and issues a reset token or link.

*Steps (Reuse Variant):*

- Initiate a password reset. Use the token to complete a password change.
- Submit the same token again to the reset endpoint. Observe the response.

*Steps (Expiry Variant):*

- Initiate a password reset. Do not use the token.
- Wait until the expiry window passes. Submit the expired token. Observe the response.

*Expected Result:* +
Both variants return an error indicating the token is invalid or expired. No password change is performed. HTTP response is 400 or 422.

*Failure Condition:* The system accepts a reused or expired token and performs a password change.

[cols="1,3", options="header"]

*Preconditions:* +
Registration form is accessible. No prior session exists. +
Acceptance criteria per US.AUTH.01: "Given missing required fields, when submission is attempted, then inline validation errors are displayed."

*Steps:*

- Submit the form with all fields empty. Observe validation output.
- Enter malformed email values in sequence (`notanemail`, `user@`, `@domain.com`). Attempt submission for each.

*Expected Result:* +

*Failure Condition:* Any invalid input produces an account, or errors are absent or not field-specific.

===== Assumptions

The following assumptions were made due to information not yet documented in the project artifact. Sections 2.2.3, 2.2.4, and 2.2.5 of the project documentation are currently empty. These assumptions must be resolved before test execution begins.

- The system issues bearer tokens that carry a role claim. Token format and structure have not been specified. Technology stack remains undecided as of Milestone 1.
- Password reset uses a token-based email link mechanism. No reset flow has been documented in the artifact.
- Account states include at minimum active and deactivated. A complete state enumeration has not been provided. The artifact references deactivation in Epic E5 without defining the full state model.
- A role-less account state is reachable either as a transient post-registration condition or as an administrative edge case. The role assignment mechanism has not been confirmed.
- Session token expiry exists. Duration is unknown. Server-side invalidation on logout is expected but has not been specified.
- Email verification is required before a new account can authenticate. This has not been explicitly stated in the artifact.
- No failed-login lockout policy has been defined. If a lockout policy is introduced, TC-05 must be updated accordingly.
